## Combined selected coverage and marginal value

| Capability / production situation | Core alone remains responsible for | Data-migration adds | Reliable-event-processing adds | Residual boundary |
|---|---|---|---|---|
| C01–C03 intent/context/contracts | Understand actual supported obligations and authority | Historical row meaning, readers/writers and finite transition completion criteria | Event identity, delivery versus effect, acknowledgement and replay obligations | Product support/retention/SLO choices remain owner supplied |
| C04–C08 design, tests and construction | Coherent scope, alternatives, meaningful evidence, preservation | Explicit intermediate-state matrix, resumable bounded transformation and reconciliation | Effect/ack state machine, deduplication or compensation boundary, retry/dead-letter policy | Current database/broker semantics remain verified, not assumed |
| C09–C13 diagnosis/state/fault/performance | Ground hypotheses, preserve invariants, qualify workload/fault claims | Interrupted batches, concurrent writes, convergence, cutover and honest recovery limits | Crash windows, duplicate and out-of-order delivery, poison messages, recovery progress | Shared-memory models, consensus implementations and stream windows are not supplied |
| C14–C19 dependencies/review/release/handoff/proportion/security | Review substance, native mechanics, accurate status and relevant controls | Cleanup gates, mapping exceptions, evidence for contraction and sensitive-data handling | Redelivery visibility, bounded retries/backpressure, effect reconciliation and sensitive-event handling | Neither pack is an operations platform, security policy or universal runtime |

Two selections follow two distinguishable recurring production needs: **a finite evolution of existing durable state** and **continuing event-driven effects under failure**. They share invariants, explicit evidence and compatibility because these are core obligations. Their marginal specialised outputs differ: a transition/reconciliation/contraction account versus an effect/acknowledgement/replay account. A database-backed event consumer may use both only where both apply; the default is not to load both for every database change.

The pool supports neither a language-per-pack catalogue nor a claim that these two cover every specialist need. Browser/mobile lifecycle, native runtime concurrency, stream-time semantics, low-latency workloads and deep security remain explicit expansion candidates. They remain deferred rather than disguised as complete packs. There is no minimum catalogue count inferred from five foundational books.

## Initial pack model and precedence

A pack is optional, reusable decision guidance with an activation boundary, constraints/defaults, core-command effects and falsifiable acceptance cases. It differs from a framework prompt by qualifying assumptions and changing observable decisions, tests and artifacts; it differs from a project README by transferring across independent cases; it differs from an external specialist skill by refining this domain's complete workflow without replacing native execution or claiming another domain's authority.

Precedence is explicit project instructions → accepted architecture/public contracts/approved work → selected pack → core defaults. A discovered conflict is surfaced against the actual decision; a pack cannot silently replace stronger accepted work. The engineering core remains useful without packs. Evaluation preserves intentional specialised traits while rejecting actual invariant, compatibility, security, evidence or authority defects. A justified one-shot migration or non-transactional compensated effect is not wrong merely because a soft pack default prefers another method.

Installed packs must carry their necessary runtime guidance locally; source reuse is a research technique, not inheritance from books, logs, another pack or a family repository. The authoring contract and final P5 profiles will specify packaging/evaluation details without introducing a generic dispatcher or metadata runtime.
