# Software Engineering Skills: Extension Packs Specification

**Version:** 1.0 · **Date:** 13 September 2026

**State:** canonical implementation specification; source/behaviour/installation readiness is reported separately.

**Owns:** pack model/dimensions, activation/precedence, core integration, verification/evaluation, packaging, authoring, source/evidence and boundaries.

This specification is derived from the persisted bootstrap research accepted through Stage 14 (`9c84caf8d535aedf8f774a30dfc90a9038315d6a`). Normative operational requirements are stated here; linked research preserves provenance and limitations. A requirement is not evidence that it has been implemented or passed. User/project authority outranks defaults.

## Pack model and boundaries

An Extension Pack is optional reusable engineering guidance that materially specialises the core's decisions, verification and evaluation for a bounded recurring production need. It is not a project README, language encyclopedia, provider adapter, executable policy engine or replacement for the core. Core still owns intent, contracts, diagnosis, preservation, truthful evidence, security and proportion without any pack.

Select a pack because the actual task and explicit user/project selection make it applicable, not because a source file uses SQL or async syntax. An explicit incompatible selection receives a precise explanation and bounded appropriate route; do not invent a migration or broker. Do not load all packs by default. Either selected pack works without the other.

## Specialisation dimensions and catalogue decisions

Six language/runtime dimensions, six framework dimensions, seven architecture dimensions and six engineering-risk dimensions were compared with project-context/core alternatives. The actual dispositions and rationale follow; they determine why only two entries were selected. Reuse of an external candidate means inspect applicable licensed guidance/tools, not copy its whole contents or activate all its instructions.
## Assessed dimensions

In the coverage column: **L** language/runtime semantics; **F** framework lifecycle and integration; **A** public interface evolution; **D** durable-state transition; **E** ongoing event effects, ordering and recovery; **Q** workload/security/operational constraints. These are overlapping responsibilities, not scores. Native core obligations remain present even when a pack deepens one.

## Complementary responsibility

| Capability / production situation | Core alone remains responsible for | Data-migration adds | Reliable-event-processing adds | Residual boundary |
|---|---|---|---|---|
| C01–C03 intent/context/contracts | Understand actual supported obligations and authority | Historical row meaning, readers/writers and finite transition completion criteria | Event identity, delivery versus effect, acknowledgement and replay obligations | Product support/retention/SLO choices remain owner supplied |
| C04–C08 design, tests and construction | Coherent scope, alternatives, meaningful evidence, preservation | Explicit intermediate-state matrix, resumable bounded transformation and reconciliation | Effect/ack state machine, deduplication or compensation boundary, retry/dead-letter policy | Current database/broker semantics remain verified, not assumed |
| C09–C13 diagnosis/state/fault/performance | Ground hypotheses, preserve invariants, qualify workload/fault claims | Interrupted batches, concurrent writes, convergence, cutover and honest recovery limits | Crash windows, duplicate and out-of-order delivery, poison messages, recovery progress | Shared-memory models, consensus implementations and stream windows are not supplied |
| C14–C19 dependencies/review/release/handoff/proportion/security | Review substance, native mechanics, accurate status and relevant controls | Cleanup gates, mapping exceptions, evidence for contraction and sensitive-data handling | Redelivery visibility, bounded retries/backpressure, effect reconciliation and sensitive-event handling | Neither pack is an operations platform, security policy or universal runtime |

Two selections follow two distinguishable recurring production needs: **a finite evolution of existing durable state** and **continuing event-driven effects under failure**. They share invariants, explicit evidence and compatibility because these are core obligations. Their marginal specialised outputs differ: a transition/reconciliation/contraction account versus an effect/acknowledgement/replay account. A database-backed event consumer may use both only where both apply; the default is not to load both for every database change.

The pool supports neither a language-per-pack catalogue nor a claim that these two cover every specialist need. Browser/mobile lifecycle, native runtime concurrency, stream-time semantics, low-latency workloads and deep security remain explicit expansion candidates. They remain deferred rather than disguised as complete packs. There is no minimum catalogue count inferred from five foundational books.

## Activation, precedence and core integration

Use this precedence within applicable higher-level instructions: explicit project instructions → accepted architecture, public contracts and approved work → selected pack → core defaults. Evidence can reveal a genuine contradiction, which is surfaced to the actual owner when standing authority cannot resolve it; the pack cannot silently rewrite support, data meaning, trust, loss/retention or product policy. Existing authority persists.

A pack changes selected questions, approaches, tests and findings inside the same workflow. CMD01 inspects specialised history/effects and real bindings; CMD02 compares adequate paths and recovery; CMD03 implements the chosen bounded path; CMD04/05 add relevant discriminating checks; CMD06 preserves cause/unknown state; CMD07 reports actual completion and receiving needs. Evaluator CMD08–12 assesses relevant specialised traits and real defects under its unchanged assessment-only boundary. No compulsory command chain or central pack resolver is created.

Hard constraints express actual accepted semantics, support, authority and evidence truth. Soft defaults are conditional methods: additive migration when overlap demands it, bounded batches when useful, local atomic effect/identity when participants support it, stable identity/status for cooperative external services, scoped ordering and actual retry policy. A valid exclusive one-shot migration, compensated workflow or best-effort telemetry policy can be correct. No universal dual-write, three-release, outbox, global-order, retry-count, permanent-deduplication or exactly-once external-effect mandate.

## Verification changes and pack-aware evaluation

Add only tests needed for the actual specialised obligations. Migration checks meaning/history, actual old/new readers/writers, interruption/progress, concurrent updates, exceptions, reconciliation and contraction/recovery eligibility. Event checks actual identity/effect/ack binding, repeat/mismatch/tenant distinctions, concurrency/crash, unknown external outcomes, required order, poison/replay/retention and retry ownership. Real local database evidence and controlled delivery/carrier models are labelled at their actual scope; they do not certify production broker/database guarantees or workloads.

Evaluation preserves justified intermediate duplicate representations or necessary identity/recovery state while rejecting corruption, lost updates, duplicate/lost effects, wrong oracles, unsupported guarantees and stale evidence. Keep all twelve qualities separate; pack terminology/extra prose does not earn a better score. Specification 04 owns equal-task comparisons and full execution conditions; Specification 06 owns the exact DMC/EPC mappings and current status.

## Packaging and independent runtime use

Package `packs/<slug>/PACK.md` with concise identity, use/non-use, activation, precedence, hard/default guidance, relevant core decisions, verification/quality, boundaries and local resource routing. Store necessary detailed guidance and concise provenance under that pack's own `references/` directory. Use ordinary Markdown, not a new metadata DSL/interpreter. Install the selected folder with its local layout preserved and supply its actual installed path to the active skill through the host-supported request/project selection mechanism.

Core skills remain under `skills/` with SKILL.md discovery. PACK.md is explicitly selected guidance, not an additional advertised standalone core skill. A consumer can place packs in `.agents/software-engineering-packs/` or another explicit path; the core must not assume access to source-checkout `packs/`. Every referenced runtime file stays inside the selected installation. No original book, research-log, family repository, source benchmark, sibling pack or shared Python module is required for ordinary pack use.

Provenance links support maintainer research; they are not mandatory runtime fetches. If a task needs current vendor semantics, use actual applicable authoritative documentation and version, with missing access reported honestly. The pack itself does not auto-install a database, broker, provider or new toolchain.

## Domain-native authoring contract

An explicit request to create/refine/research/evaluate a software-engineering pack selects engineering's local `references/pack-authoring.md` workflow. It must be operational without the source research folder; new research can legitimately require user/source inputs, but this is not a hidden dependency of an already installed pack. No third creator entrypoint or thirteenth application command is introduced.

## Authoring need and catalogue decision

For a new catalogue, generate/research a broader candidate pool and compare combined coverage, practical reuse, distinct production behaviour, depth, evaluation feasibility and overlap. For a single new/revised pack, inspect only the relevant catalogue neighbourhood and core gaps. Classify the need as existing capability/pack reuse, project instructions, core improvement, reusable specialised pack, or insufficient-value/evidence defer/reject. Names, frameworks or five books do not determine catalogue size.

Preserve existing entries, installed interfaces, accepted examples and evidence. A merge/retirement/renaming needs an explicit migration decision within actual authority; a catalogue rewrite is not implied by one new pack. Record the selected entry's marginal contribution and residual gaps.
## P1–P7 and direct entry

Each P-stage is substantive, persisted and reviewed before dependent work. Use the user's commit granularity: in this bootstrap, one commit contains the complete top-level stage and its distinct internal P-records; do not split it into extra branch commits. Adequate existing evidence may satisfy a prerequisite after actual review; a narrow revision revisits affected claims/tests instead of rerunning unrelated research. The requested completion boundary and existing authorisation determine how far to continue, not an arbitrary pause at each stage.

The five-book rule allows reuse from core or other packs after checking the **specific contribution**, not five new acquisitions. Shared findings do not become independent corroboration. A supplied-book substitution already expressly authorised in the session need not be authorised again; its identity and scope must be recorded. Do not publish source files, private locations, reconstructed chapters or proprietary examples.
## Source and execution evidence expectations

Compare artifacts and decisions, not whether the run says a pack name. Core must receive the actual production need and the same substantive constraints as packed. Retain exact prompts, immutable input/candidate/core/pack identity where available, real commands/results, model/tool settings where relevant, environmental differences and resource limits. Disclose evaluator provenance, answer leakage controls and stochastic/sample limitations. A single example is not evidence of general superiority.

Pack-aware evaluation preserves intentional specialisation—for example, temporary duplicate representations in a justified migration or necessary recovery identity in an event worker—while rejecting data loss, duplicate effects, wrong oracles, unsupported guarantees or authority violations. Repair the violated obligation at the smallest coherent scope. Optional core+project-instructions comparison can test reusable prompting value; it is not permission to give only one arm a richer task.

If a comparison finds no useful difference, it is valid evidence. Revise the affected profile/tests or retain an unproven/deferred entry. Do not quietly weaken acceptance, erase a failed run, report a model simulation as provider integration, or declare external installation from local file validation.
## Maintenance and status

Necessary installed rules and references must resolve locally in the selected skill/pack. No runtime inheritance from central family docs, research logs, source-checkout tests, other packs or a custom registry. Optional providers/MCPs remain existing capabilities with explicit prerequisites. Native repository tools remain authoritative for builds/tests/deployment; authoring does not introduce a universal executor.

A change to reused source guidance triggers a bounded impact review of consuming profile/tests. Preserve unaffected productions and historical results; mark affected evidence stale instead of rewriting its past outcome. Track research, implementation, evaluation and readiness separately. Catalogue specifications show actual selected/deferred entries and evidence links; a ready claim requires demonstrated behaviour and clean use. The repository's own maturity is a separate Stage 22 assessment.

## Pack system acceptance

Research must retain exactly five justified books for each selected pack, real direct/reviewed extraction, current independent challenge, source/behaviour/test joins and explicit limitations. Never silently replace, remove or demote a supplied book; the user's requirements-book replacement is already approved and remains in force. Do not publish PDFs, private locations, reconstructed chapters or proprietary examples. Reuse the actual contribution after inspecting original evidence, not merely the bibliography.

Implementation acceptance requires actual domain-authoring creation/refinement, a self-contained pack, realistic executed showcase, actual artifacts/run history, behavioural checks and local validation. Evaluation requires fair core/core+pack showcase and independent reuse, relevant activation/non-use/precedence/preservation/negative/fidelity/refinement cases and clean external use. Record negative/null/inconclusive outcomes; refine a real gap or retain unproven status. Never weaken the core task or oracle to force a win. A directory or P1–P5 research pass is not ready-to-use evidence.
